# II. ПРОЕКТИРОВАНИЕ СИСТЕМЫ

## 2.1. Постановка задачи и требования к системе

В рамках данной дипломной работы разрабатывается web-приложение, демонстрирующее использование искусственного интеллекта и поведенческого анализа для повышения безопасности онлайн-транзакций. Основная идея системы заключается в том, что решение о выполнении транзакции должно приниматься не только на основании факта успешной авторизации пользователя, но и с учётом дополнительных факторов риска: поведения пользователя во время сессии и вероятности того, что URL-адрес или контекст операции связан с phishing-атакой.

Разрабатываемая система ориентирована на сценарий, в котором пользователь выполняет вход в приложение, взаимодействует с интерфейсом, создаёт поведенческую сессию, а затем инициирует транзакцию. Во время работы frontend-часть фиксирует события клавиатуры и мыши, backend сохраняет их в структурированном виде, модуль машинного обучения извлекает поведенческие признаки и оценивает аномальность текущей сессии. Параллельно phishing-модуль анализирует URL-адрес, связанный с транзакцией, и определяет вероятность того, что ресурс является подозрительным или вредоносным.

Итоговое решение по транзакции формируется на основе гибридной модели риска. Если URL классифицирован как phishing, транзакция блокируется. Если URL является подозрительным, система требует дополнительную проверку. Если поведение пользователя является аномальным, операция также переводится в режим дополнительного подтверждения. Если риски не обнаружены, транзакция разрешается. Таким образом, система реализует risk-based authentication, при которой уровень контроля зависит от контекста и поведения пользователя.

Основная задача проектирования заключается в создании архитектуры, которая разделяет сбор данных, извлечение признаков, ML-инференс, кэширование, принятие решения и аудит. Такое разделение необходимо для обеспечения тестируемости, расширяемости и соответствия принципам SOLID. Например, модуль извлечения признаков URL не должен отвечать за HTTP-ответы, ML-детектор не должен управлять базой данных, а frontend не должен принимать финальное решение о безопасности транзакции.

С точки зрения пользовательских сценариев система поддерживает несколько основных flow. Первый сценарий — вход пользователя в приложение. При открытии страницы входа frontend может создать поведенческую сессию и начать сбор событий, не блокируя сам процесс авторизации. После успешного входа пользователь перенаправляется на dashboard, где отображается информация о собранных сессиях и событиях.

Второй сценарий — обучение персональной поведенческой модели. Пользователь выполняет enrollment: последовательно проходит пять сессий, в каждой из которых вводит контрольную фразу `.tie5Roanl` десять раз. По завершении последней сессии система автоматически обучает персональный Isolation Forest и сохраняет его как `BehaviorProfile`.

Третий сценарий — выполнение транзакции. Пользователь заполняет форму транзакции, затем проходит challenge-typing: вводит контрольную фразу для сбора поведенческих данных. Frontend передаёт данные на backend вместе с идентификатором сессии. Backend проверяет принадлежность сессии, извлекает поведенческие признаки, сравнивает с обученным профилем, выполняет phishing-анализ URL и формирует итоговое решение.

Четвёртый сценарий — административный и исследовательский анализ. Через административную панель и dashboard можно просматривать поведенческие сессии, события клавиатуры и мыши, результаты phishing-проверок, транзакции и risk assessment. Это важно не только для демонстрации работы системы, но и для объяснимости принятого решения в рамках дипломной работы.

## 2.2. Общая архитектура приложения

Разрабатываемое приложение построено как web-система с разделением на frontend, backend, базу данных и ML-компоненты. Frontend отвечает за пользовательский интерфейс и сбор поведенческих событий в браузере. Backend реализует REST API, бизнес-логику, хранение данных, ML-инференс и принятие решений. PostgreSQL используется как основное хранилище данных. ML-логика выделена в отдельные модули, что позволяет независимо развивать phishing detection и behavioral anomaly detection.

Высокоуровневая архитектура системы представлена на рисунке 2.1.

Рис. 2.1. Высокоуровневая архитектура системы

На концептуальном уровне архитектура включает следующие компоненты:

- frontend-интерфейс;
- JavaScript/TypeScript collector поведенческих событий;
- REST API backend-приложения;
- подсистему хранения поведенческих сессий и событий;
- phishing detection pipeline;
- behavioral feature extraction module;
- персональные behavioral модели (BehaviorProfile);
- behavioral anomaly detector;
- transaction risk decision service;
- audit log;
- PostgreSQL database;
- dashboard и административную панель.

Frontend-часть реализует страницы входа, enrollment, dashboard и форму транзакции. Дополнительно она содержит collector, который фиксирует события клавиатуры и мыши. Эти события не используются для принятия решения на клиенте. Frontend только собирает данные и отправляет их на backend, поскольку финальное решение безопасности должно приниматься на доверенной серверной стороне.

Backend-часть построена на Django и Django REST Framework. Внутри backend-приложения выделены несколько доменных приложений: accounts, behavior, phishing, ml_engine и transactions. Такое разделение отражает предметные области системы. Модуль behavior отвечает за хранение сессий и событий. Модуль phishing отвечает за анализ URL. Модуль ml_engine содержит ML-логику поведенческого анализа, хранение персональных моделей и training pipeline. Модуль transactions реализует создание транзакций и итоговую оценку риска.

Общий поток данных при выполнении транзакции можно описать следующим образом. Сначала пользователь взаимодействует с интерфейсом, а frontend создаёт поведенческую сессию и отправляет события клавиатуры и мыши на backend. Когда пользователь отправляет транзакцию, backend получает идентификатор поведенческой сессии, параметры транзакции и целевой URL. Затем система извлекает поведенческие признаки, сравнивает их с обученным персональным профилем, выполняет оценку аномальности, проверяет URL на phishing и объединяет результаты в итоговом решении.

Поток обработки транзакции представлен на рисунке 2.2.

Рис. 2.2. Поток обработки транзакции

Логически обработка транзакции включает следующие этапы:

1. Пользователь заполняет форму транзакции.
2. Frontend переводит пользователя на шаг challenge-typing.
3. Пользователь вводит контрольную фразу, frontend собирает события клавиатуры и мыши.
4. Frontend отправляет параметры транзакции на endpoint `POST /api/transactions/attempts/` с `behavior_session_id`.
5. Backend проверяет, что пользователь аутентифицирован и сессия принадлежит ему.
6. `BehaviorFeatureExtractor` извлекает числовые признаки из событий.
7. `BehaviorAnomalyDetector.from_user_profile()` загружает обученную модель пользователя и оценивает аномальность поведения.
8. Если указан `target_url`, phishing service выполняет проверку URL.
9. Transaction service создаёт `TransactionAttempt` и `RiskAssessment`.
10. Decision logic возвращает итоговое решение: `ALLOW`, `CHALLENGE` или `DENY`.

С точки зрения безопасности frontend не принимает самостоятельных решений о разрешении или блокировке операции. Даже если frontend показывает результат пользователю, источником истины остаётся backend. Это принципиально важно, поскольку клиентская часть может быть изменена пользователем или злоумышленником. Поэтому все проверки принадлежности сессий, вызовы ML-модулей и итоговая decision matrix выполняются на серверной стороне.

Таким образом, архитектура приложения построена как модульная risk-based система. Она объединяет phishing detection, behavioral anomaly detection и транзакционную бизнес-логику, но при этом сохраняет разделение ответственности между компонентами. Это обеспечивает расширяемость, тестируемость и возможность дальнейшего развития системы.

## 2.3. Модель данных системы

Модель данных разработанной системы отражает основные сущности, необходимые для демонстрации аутентификации транзакций на основе phishing-риска и поведенческого анализа. В отличие от классических банковских систем, целью данной работы является не реализация полноценного финансового ядра, а построение исследовательского прототипа, в котором можно проследить полный путь данных: от пользовательского поведения в браузере до итогового решения по транзакции.

В системе можно выделить несколько групп сущностей:

- сущности пользователей и аутентификации;
- сущности поведенческого анализа и персональных моделей;
- сущности phishing-детекции;
- сущности транзакций и оценки риска;
- вспомогательные сущности аудита и хранения результатов анализа.

Центральной сущностью пользовательской активности является `BehaviorSession`. Она представляет отдельный период взаимодействия пользователя с приложением, в рамках которого собираются события клавиатуры и мыши. Поле `is_enrollment` маркирует сессию как часть enrollment-процесса обучения модели. Такая сессия может быть связана с авторизованным пользователем, а в демонстрационном или pre-auth сценарии может временно существовать без пользователя. Возможность создания анонимных поведенческих сессий управляется конфигурационным параметром.

Основные поля `BehaviorSession` включают идентификатор сессии, пользователя, время начала, время завершения, контекст, IP-адрес, user-agent и признак enrollment-сессии. Использование UUID в качестве идентификатора удобно для browser-facing API, поскольку такой идентификатор сложнее предсказать, чем последовательный integer id.

События клавиатуры хранятся в сущности `KeystrokeEvent`. Каждое событие связано с конкретной `BehaviorSession` и содержит тип события, код клавиши, временную метку, относительное время с начала сессии, а также вычисленные параметры dwell time (время удержания клавиши) и flight time (интервал между клавишами). Исходное значение введённого символа не сохраняется в открытом виде — если frontend передаёт `key_value`, backend сохраняет только его хеш.

События мыши хранятся в сущности `MouseEvent`. Они описывают движения курсора, клики и скроллинг. Для таких событий сохраняются координаты, тип события, кнопка мыши, величина прокрутки, временная метка и дополнительные metadata. Эти данные используются для вычисления агрегированных признаков: длины траектории, скорости движения, количества кликов и активности в рамках сессии.

Персональные поведенческие модели хранятся в сущности `BehaviorProfile`. Она имеет связь OneToOne с пользователем, содержит сериализованную Isolation Forest модель в поле `model_blob` (BinaryField), поля версионирования, количество обучающих сессий и векторов, диагностические метрики и флаг активности. Именно эта сущность отличает систему от подхода с нефиксированным в-памяти baseline: каждый пользователь имеет собственную обученную модель.

Отдельную группу составляют сущности phishing-модуля. Основной сущностью аудита является `PhishingEvent`, в которой сохраняются URL, результат классификации, вероятность phishing, вероятность легитимности и связанный контекст.

Транзакционный модуль содержит сущность `TransactionAttempt`. Она представляет попытку выполнения операции пользователем. Результат анализа транзакции сохраняется в `RiskAssessment`. Эта сущность фиксирует итоговое решение системы, phishing-score, behavior-score, дополнительные объяснения и служебные данные.

Упрощённая логическая структура данных представлена в таблице 2.3.

Таблица 2.3. Основные сущности системы

| Сущность | Назначение | Основные связи |
|---|---|---|
| User | Пользователь приложения | Связан с поведенческими сессиями, профилем и транзакциями |
| BehaviorSession | Поведенческая сессия пользователя | Связана с User, KeystrokeEvent, MouseEvent |
| KeystrokeEvent | Событие клавиатуры | Связано с BehaviorSession |

Рис. 2.3. ER-диаграмма основных сущностей системы

При проектировании модели данных учитывались требования безопасности и приватности. Наиболее важным решением является отказ от хранения исходного текста, вводимого пользователем. Это особенно важно в контексте форм входа и транзакций, где могут присутствовать пароли, имена получателей, комментарии или другие чувствительные данные. Вместо этого система хранит технические и временные характеристики событий, а также хеши отдельных значений, если это необходимо для анализа.

Дополнительно модель данных поддерживает auditability. Система сохраняет не только итоговое решение, но и промежуточные результаты: phishing-score, behavior-score, decision reason и признаки, использованные для анализа. Это важно для объяснимости, поскольку в системах безопасности недостаточно просто заблокировать действие. Необходимо иметь возможность показать, какие факторы повлияли на решение: подозрительный URL, аномальное поведение, высокая сумма операции или ошибка внешней проверки.

Таким образом, модель данных системы поддерживает полный цикл работы приложения: сбор поведенческих событий, обучение персональных моделей, хранение phishing-проверок, создание транзакций, сохранение risk assessment и последующий аудит.

## 2.4. Подсистема сбора поведенческих данных

Подсистема сбора поведенческих данных предназначена для фиксации действий пользователя во время взаимодействия с web-интерфейсом. Её задача состоит не в том, чтобы записывать содержание вводимых данных, а в том, чтобы сохранить технические характеристики поведения: временные интервалы, количество событий, координаты курсора, клики и другие признаки, которые могут быть использованы для последующего анализа.

Сбор данных начинается на frontend-стороне. При открытии страницы входа, dashboard или формы транзакции collector может создать поведенческую сессию через backend API. После этого frontend фиксирует события клавиатуры и мыши и периодически отправляет их на сервер батчами. Такой подход уменьшает количество сетевых запросов и позволяет не блокировать пользовательский интерфейс при каждом событии.

Для создания поведенческой сессии используется endpoint `POST /api/behavior/sessions/`. В запросе передаётся контекст сессии, например страница, сценарий или признак enrollment. Backend создаёт `BehaviorSession` и возвращает её идентификатор. Этот идентификатор затем используется при отправке событий клавиатуры и мыши. Для завершения сессии используется endpoint `POST /api/behavior/sessions/{session_id}/end/`.

События клавиатуры отправляются через endpoint `POST /api/behavior/sessions/{session_id}/keystrokes/`. Запрос содержит массив событий. Каждое событие включает тип события, код клавиши, временную метку, относительное время с начала сессии и дополнительные параметры, если они были вычислены на клиенте. При этом исходное значение символа не сохраняется в открытом виде.

События мыши отправляются через endpoint `POST /api/behavior/sessions/{session_id}/mouse/`. Такие события содержат тип действия, координаты курсора, кнопку мыши, величину прокрутки и временные параметры. На основе этих данных backend впоследствии может вычислить длину траектории, скорость движения, количество кликов и другие признаки.

Подсистема сбора данных построена так, чтобы ошибка collector-а не блокировала основной пользовательский сценарий. Например, если после успешного логина не удалось создать поведенческую сессию, пользователь всё равно должен попасть в dashboard.

Особое внимание уделяется защите чувствительных данных. При обработке клавиатурных событий система не сохраняет исходный введённый символ. Если frontend передаёт `key_value`, backend использует его только для вычисления SHA-256 hash, после чего сохраняет только `key_value_hash`. Такой подход позволяет подтвердить факт обработки клавиши, но не позволяет восстановить введённый текст. Это особенно важно для полей пароля и других конфиденциальных данных.

Batch creation вынесен в service layer. View отвечает за получение HTTP-запроса, вызов serializer-а и формирование ответа. Service отвечает за создание записей в базе данных. Такое разделение улучшает читаемость кода и соответствует принципу единственной ответственности.

Подсистема также предоставляет summary endpoint `GET /api/behavior/sessions/{session_id}/summary/`, который возвращает краткую информацию о сессии: идентификатор, длительность, количество событий клавиатуры, количество событий мыши и признак enrollment.

Собранные события сами по себе ещё не являются ML-признаками. Они представляют сырой слой данных, из которого затем извлекаются агрегированные характеристики. Например, отдельные `keydown` и `keyup` события преобразуются в среднее время удержания клавиш, а последовательность координат мыши — в длину траектории и скорость движения. Такое разделение позволяет независимо развивать collection layer и ML layer.

## 2.5. Подсистема обнаружения phishing-атак

Подсистема обнаружения phishing-атак предназначена для автоматической оценки URL-адресов, связанных с пользовательскими действиями и транзакциями. Её основная задача — определить, является ли URL легитимным, подозрительным или phishing, а также предоставить числовую вероятность риска, которую можно использовать при принятии решения по транзакции.

Архитектура phishing-модуля построена в виде последовательного pipeline. Входом является URL-адрес, а выходом — объект с вероятностью phishing, вероятностью легитимности, итоговым решением и набором вычисленных признаков. Такой подход позволяет отделить процесс извлечения признаков от ML-инференса и decision logic.

Первым этапом является извлечение признаков. В системе используется структура `URLFeatures`, содержащая признаки, совместимые с подходом, применяемым в UCI Phishing Websites Dataset. Признаки делятся на несколько групп: лексические, SSL, WHOIS/DNS, HTML и внешние репутационные признаки.

Лексический extractor анализирует сам URL без сетевых запросов. Он вычисляет признаки, связанные с наличием IP-адреса, длиной URL, использованием сокращателей, символом `@`, двойным слешем, дефисами в домене, количеством поддоменов и наличием HTTPS-токена в доменной части. Эти признаки быстро вычисляются и являются первым слоем анализа.

SSL extractor отвечает за проверку состояния HTTPS/SSL. Наличие корректного сертификата само по себе не гарантирует легитимность ресурса, поскольку phishing-сайты также могут использовать HTTPS. Однако состояние SSL остаётся полезным признаком, особенно в сочетании с другими характеристиками.

WHOIS extractor анализирует доменные признаки: возраст домена, срок регистрации, наличие DNS-записи и связанные сетевые параметры. Такие признаки помогают выявлять недавно созданные домены, которые часто используются в phishing-кампаниях.

HTML extractor анализирует содержимое web-страницы. Он может учитывать favicon, внешние request URL, anchors, links in tags, формы, отправку данных на email, перенаправления, JavaScript-события, всплывающие окна и iframe.

External extractor отвечает за внешние признаки, включая web traffic на основе локального Tranco-списка. Часть внешних признаков в демонстрационной реализации может возвращать нейтральное значение — это допустимо для исследовательского прототипа, если явно документировано.

Для объединения extractor-ов используется `URLFeatureExtractor`. Лексический extractor выполняется первым синхронно, а остальные extractor-ы запускаются параллельно через `ThreadPoolExecutor`. Если один из extractor-ов падает или не успевает завершиться за заданный timeout, его признаки остаются равными default-значениям, а pipeline продолжает работу. Такой подход обеспечивает graceful degradation.

После извлечения признаков используется `FeatureCache`. Кэширование необходимо, поскольку многие URL могут проверяться повторно, а часть extractor-ов выполняет дорогие сетевые операции. Ключ кэша строится на основе нормализованного URL и версии структуры признаков.

ML-инференс выполняется в `XGBoostPhishingDetector`. Detector загружает сохранённый model artifact из пути, заданного через настройку `PHISHING_MODEL_PATH`. Detector преобразует `URLFeatures` в feature vector в стабильном порядке, вызывает `predict_proba` и получает вероятность phishing-класса.

Итоговое решение phishing-модуля формируется на основе threshold-логики: `legitimate`, `suspicious` или `phishing`. Результат проверки доступен через endpoint `POST /api/phishing/check/`. При успешной проверке результат сохраняется в `PhishingEvent`, что обеспечивает аудит и возможность последующего анализа.

Phishing-модуль используется двумя способами. Во-первых, его можно вызывать напрямую для проверки URL. Во-вторых, он используется внутри transaction flow, когда пользователь создаёт транзакцию и указывает `target_url`. В этом случае phishing-риск становится одним из факторов итогового решения.

## 2.6. Подсистема поведенческого анализа

Подсистема поведенческого анализа выполняет три взаимосвязанные функции: преобразование сырых поведенческих событий в числовые признаки, обучение персональной модели аномалий для каждого пользователя и последующий инференс при транзакционных проверках. В отличие от подхода с единым нефиксированным baseline-детектором, реализованная архитектура строит и сохраняет отдельную Isolation Forest модель для каждого пользователя, что обеспечивает персонализированную оценку отклонений.

**Архитектура подсистемы.** Подсистема состоит из четырёх ключевых компонентов, каждый из которых несёт единственную ответственность согласно принципу SRP:

| Компонент | Модуль | Ответственность |
|---|---|---|
| `BehaviorFeatureExtractor` | `behavior_features.py` | Преобразование событий в числовой вектор |
| `BehaviorProfileTrainer` | `training.py` | Обучение и сохранение персональной модели |
| `BehaviorProfile` | `models.py` | Хранение сериализованной модели и метаданных |
| `BehaviorAnomalyDetector` | `behavior_detectors.py` | Загрузка профиля и инференс |

**Извлечение признаков.** Класс `BehaviorFeatureExtractor` предоставляет два метода, предназначенных для разных режимов работы. Метод `extract(session)` применяется при инференсе: он агрегирует все события одной сессии в единый вектор признаков `BehaviorFeatures`. Метод `extract_repetitions(session)` применяется при обучении: он разбивает одну сессию на отдельные повторения и возвращает список `list[BehaviorFeatures]` — по одному вектору на каждое повторение. Такое разделение решает принципиальную проблему: в enrollment-сессии пользователь вводит фразу `.tie5Roanl` десять раз подряд. Если рассматривать всю сессию как один вектор, то для Isolation Forest, которому требуется не менее 50 наблюдений, потребовалось бы 50 сессий. Разбиение каждой сессии на 10 повторений позволяет получить 50 обучающих векторов уже из 5 сессий.

Разбиение реализовано в методе `_detect_repetition_boundaries()` через адаптивный алгоритм на основе критерия Тьюки (Tukey's fence) [TUKEY 1977]. Метод анализирует временны́е интервалы между событиями `keyup` внутри сессии. Для вычисления порогового значения используется формула: `threshold = median(gaps) + 3 × IQR(gaps)`, где IQR — межквартильный размах. Использование медианы и IQR вместо среднего и стандартного отклонения обусловлено их устойчивостью к выбросам (robust statistics): крупные межповторные паузы, которые мы как раз и пытаемся детектировать, не искажают порог, как это произошло бы при использовании среднего. Дополнительно применяется нижний порог `MIN_GAP_THRESHOLD_MS = 400 мс`, который предотвращает ложное разбиение при высокой скорости набора. Если адаптивное пороговое значение не превышает этот минимум, он используется вместо него. Таким образом, алгоритм является самонастраивающимся: он работает независимо от индивидуальной скорости набора пользователя.

Структура данных `BehaviorFeatures` является неизменяемым датаклассом (`frozen=True`), содержащим 16 числовых полей. Эти поля разделены на три логические группы в соответствии с природой источника данных.

Таблица 2.4. Поведенческие признаки системы

| Группа | Признак | Описание |
|---|---|---|
| Session | `session_duration_ms` | Длительность поведенческой сессии, мс |
| Keyboard | `keystroke_count` | Суммарное количество событий клавиатуры |
| Keyboard | `keydown_count` | Количество событий нажатия клавиши |
| Keyboard | `keyup_count` | Количество событий отпускания клавиши |
| Keyboard | `avg_dwell_time_ms` | Среднее dwell time (время удержания клавиши), мс |
| Keyboard | `std_dwell_time_ms` | Стандартное отклонение dwell time |
| Keyboard | `avg_flight_time_ms` | Среднее flight time (интервал между клавишами), мс |
| Keyboard | `std_flight_time_ms` | Стандартное отклонение flight time |
| Keyboard | `typing_speed_keys_per_second` | Скорость набора (нажатий в секунду) |
| Mouse | `mouse_event_count` | Суммарное количество событий мыши |
| Mouse | `mouse_move_count` | Количество событий перемещения курсора |
| Mouse | `mouse_click_count` | Количество кликов |
| Mouse | `mouse_scroll_count` | Количество событий скроллинга |
| Mouse | `mouse_path_length` | Длина траектории курсора (пикселей) |
| Mouse | `avg_mouse_speed` | Средняя скорость движения мыши |
| Mouse | `max_mouse_speed` | Максимальная скорость движения мыши |

Метод `to_vector()` возвращает признаки в фиксированном порядке, совпадающем с порядком полей датакласса. Стабильность этого порядка критична: ML-модель принимает не именованный словарь, а числовой вектор, поэтому перестановка признаков без переобучения приведёт к некорректным результатам инференса. Этот инвариант покрыт автоматическими тестами.

**Персональная поведенческая модель.** Обученная Isolation Forest модель сохраняется в Django-модели `BehaviorProfile`. Связь с пользователем реализована через поле `OneToOneField`, что гарантирует наличие не более одного активного профиля на пользователя. Сериализованная модель хранится в поле `model_blob` типа `BinaryField` — serialization выполняется библиотекой joblib непосредственно в байтовый буфер.

Версионирование реализовано через два поля: `feature_schema_version` (текущее значение `"v1"`) и `detector_version` (текущее значение `"isolation_forest_v1"`). При изменении состава или порядка признаков в `BehaviorFeatures` необходимо увеличить `feature_schema_version`, при изменении алгоритма или гиперпараметров — `detector_version`. Если при загрузке профиля версии не совпадают с актуальными константами в `training.py`, детектор возвращает решение `suspicious` (cold start fallback), не допуская применения несовместимой модели. Поля `training_score_mean` и `training_score_std` сохраняют диагностические метрики, позволяя оценить распределение аномальных оценок на обучающих данных без повторного запуска модели.

**Процесс обучения.** Класс `BehaviorProfileTrainer` реализует pipeline обучения персональной модели. Метод `train(user)` выполняет следующую последовательность шагов:

1. Сбор всех завершённых enrollment-сессий пользователя (`is_enrollment=True`, `ended_at` заполнено).
2. Извлечение per-repetition feature vectors из каждой сессии через `BehaviorFeatureExtractor.extract_repetitions()`.
3. Проверка минимальных порогов: не менее `MIN_ENROLLMENT_SESSIONS = 5` сессий и не менее `MIN_TRAINING_SAMPLES = 50` обучающих векторов. При недостаточном количестве данных возвращается `TrainingResult(success=False, error=...)`.
4. Обучение `IsolationForest` с параметрами `contamination=0.1`, `n_estimators=100`, `random_state=42` на всех собранных векторах.
5. Вычисление диагностических метрик `training_score_mean` и `training_score_std` на обучающей выборке.
6. Сериализация модели через joblib в байтовый буфер.
7. Атомарное сохранение через `BehaviorProfile.objects.update_or_create()` — если профиль уже существует, он заменяется новым; поле `is_active` устанавливается в `True`.

Результат возвращается в виде `TrainingResult`, содержащего флаг успеха, ссылку на сохранённый профиль, количество сессий, количество векторов и, при неудаче, строку с причиной ошибки. Это позволяет frontend корректно информировать пользователя о статусе обучения.

**Инференс и cold start.** Метод класса `BehaviorAnomalyDetector.from_user_profile(user)` является основной точкой входа для инференса. Он выполняет следующую логику: сначала ищет активный `BehaviorProfile` для пользователя. Если профиль не найден или версии не совпадают с актуальными — возвращается ненастроенный детектор (`_is_fitted=False`). Если профиль найден — загружает сериализованную Isolation Forest модель через `BehaviorProfileTrainer.deserialize_model()` и возвращает настроенный детектор.

Ненастроенный детектор при вызове `predict()` возвращает `BehaviorAnomalyResult` с `decision="suspicious"`. Это deliberate choice: при cold start (нет обученного профиля) система не может объективно оценить поведение, поэтому принимает осторожную позицию. Результат `suspicious` не блокирует транзакцию автоматически, но может повысить итоговое решение до `CHALLENGE` для крупных операций.

Дополнительная проверка на достаточность данных выполняется в `TransactionAttemptService._evaluate_behavior()`: если сессия содержит менее 10 событий клавиатуры (`keystroke_count < 10`), анализ считается недостоверным и возвращается `suspicious` с причиной `"insufficient_keystrokes"`.

**Приватность.** Ни один из этапов анализа не использует фактические введённые символы. `BehaviorFeatureExtractor` работает исключительно с временными метками и координатами мыши. Персональный профиль содержит только параметры Isolation Forest, которые нельзя обратно преобразовать в исходный текст. Это позволяет реализовать персонализированную аутентификацию без накопления чувствительного текстового контента.

## 2.7. Механизм оценки риска транзакции

Механизм оценки риска транзакции является центральным элементом разрабатываемой системы. Именно он объединяет результаты phishing-детекции, поведенческого анализа и параметры самой транзакции в единое итоговое решение. В рамках данной работы решение может принимать одно из трёх значений: `ALLOW`, `CHALLENGE` или `DENY`.

**Проблема несоответствия доменов обучения и инференса.** При разработке системы возникает архитектурная сложность: поведенческая модель обучена на паттернах набора контрольной фразы `.tie5Roanl`, тогда как на обычной странице транзакции пользователь вводит произвольный текст — сумму, имя получателя, URL. Ввод произвольного текста и ввод известной фразы генерируют принципиально разные поведенческие паттерны (различный ритм, длина слов, частота ошибок), что может приводить к ложноположительным срабатываниям даже для легитимного пользователя. Данная проблема известна в машинном обучении как training/inference domain mismatch — несоответствие распределений обучающих и тестовых данных.

Для устранения этого несоответствия реализован механизм challenge-typing. При инициировании транзакции frontend не сразу отправляет запрос на сервер, а переводит пользователя на промежуточный шаг подтверждения. На этом шаге пользователю предлагается ввести контрольную фразу `.tie5Roanl` — ту же фразу, которая использовалась при enrollment. Таким образом, инференс выполняется в семантически идентичных условиях: поведенческие данные, собранные при challenge-typing, распределены так же, как и данные, на которых обучена персональная модель.

Механически challenge-typing реализован как многошаговый wizard на странице транзакции. Компонент `TransactionPage` управляет конечным автоматом с тремя состояниями:

- `form` — пользователь заполняет реквизиты транзакции (получатель, сумма, целевой URL);
- `challenge` — пользователь вводит контрольную фразу; frontend создаёт новую поведенческую сессию, фиксирует события клавиатуры и мыши;
- `result` — отображается итоговое решение с объяснением.

При переходе к шагу `challenge` открывается новая поведенческая сессия через `collector.startSession()`. Когда пользователь завершает ввод контрольной фразы (значение поля совпадает со строкой `.tie5Roanl`), автоматически вызывается функция `submitTransaction()`. В ней критически важна последовательность операций: сначала сохраняется `activeSessionId`, затем вызывается `collector.endSession()` для корректного закрытия сессии, после чего идентификатор сессии передаётся в запрос к API. Такой порядок гарантирует, что все события challenge-typing будут зафиксированы и привязаны к правильной сессии до её отправки на backend.

**Процесс оценки риска.** Входными данными для transaction risk engine являются параметры транзакции, идентификатор пользователя, идентификатор поведенческой сессии и целевой URL. Endpoint создания транзакции требует аутентификации, поэтому anonymous user не может создать `TransactionAttempt`. Если в запросе передан `behavior_session_id`, backend проверяет, что эта сессия принадлежит текущему пользователю. Это предотвращает ситуацию, когда пользователь или злоумышленник пытается подставить чужую поведенческую сессию для снижения риска операции.

После проверки сессии выполняется поведенческий анализ. `BehaviorFeatureExtractor` извлекает признаки из связанных событий, а `BehaviorAnomalyDetector.from_user_profile()` загружает обученную персональную модель и возвращает результат анализа. Если поведение признано аномальным, итоговое решение повышается до `CHALLENGE`.

Параллельно выполняется phishing-анализ целевого URL. Если phishing-модуль возвращает решение `phishing`, transaction risk engine немедленно формирует итоговое решение `DENY`. Если phishing-модуль возвращает `suspicious`, транзакция переводится в `CHALLENGE`. Если phishing-проверка завершилась ошибкой при наличии `target_url`, система выбирает безопасное решение `CHALLENGE` в соответствии с fail-safe логикой.

Для учёта суммы транзакции используется дополнительное правило. Если поведение пользователя классифицировано как `suspicious`, а сумма транзакции превышает `HIGH_VALUE_TRANSACTION_THRESHOLD = 1000.00` MDL, операция также переводится в `CHALLENGE`. Это правило демонстрирует risk-based подход: один и тот же поведенческий сигнал может иметь разный вес в зависимости от критичности операции.

Итоговая decision matrix представлена в таблице 2.5.

Таблица 2.5. Матрица принятия решения по транзакции

| Условие | Итоговое решение | Обоснование |
|---|---|---|
| `phishing_decision = phishing` | `DENY` | URL классифицирован как phishing |
| `phishing_decision = suspicious` | `CHALLENGE` | URL требует дополнительной проверки |
| Ошибка phishing-check при наличии `target_url` | `CHALLENGE` | Невозможно безопасно подтвердить URL |
| `behavior_decision = anomalous` | `CHALLENGE` | Поведение существенно отличается от ожидаемого |
| Ошибка поведенческого анализа | `CHALLENGE` | Анализ недоступен, принимается осторожное решение |
| `behavior_decision = suspicious` и сумма `>= 1000.00` MDL | `CHALLENGE` | Повышенный риск для крупной операции |
| Иные случаи | `ALLOW` | Существенных признаков риска не обнаружено |

Важно, что итоговое решение формируется на backend-стороне. Frontend только отображает результат и причины. Это принципиально, поскольку frontend не является доверенной средой: пользователь может изменить JavaScript-код, подменить запрос или отключить collector. Поэтому все проверки принадлежности сессий, вызовы ML-модулей и формирование `RiskAssessment` выполняются сервером.

Результат анализа сохраняется в `RiskAssessment`. В этой сущности фиксируются итоговое решение, phishing score, behavior score, phishing decision, behavior decision и список reasons. Такой формат важен для explainability. В системах безопасности пользователь или администратор должен понимать, почему транзакция была разрешена, заблокирована или отправлена на дополнительную проверку.

## 2.8. Обоснование выбора технологий

Выбор технологического стека определялся задачами дипломной работы: необходимо было реализовать web-приложение с REST API, хранением данных, frontend-интерфейсом, ML-инференсом и возможностью демонстрации полного end-to-end flow. Важными критериями были зрелость технологий, доступность документации, совместимость с Python ML-экосистемой, скорость разработки и удобство тестирования.

В качестве основного backend-фреймворка выбран Django. Он предоставляет развитую инфраструктуру для работы с моделями, миграциями, административной панелью, аутентификацией и настройками окружения. Для дипломного проекта это особенно полезно, поскольку позволяет быстро создать полноценное web-приложение и сосредоточиться на исследовательской логике: phishing detection, behavioral analysis и transaction risk scoring.

Для построения REST API используется Django REST Framework. DRF предоставляет serializers, views, permissions и удобные механизмы тестирования API. Это позволяет строго разделить validation layer, service layer и response layer. Например, serializers отвечают за проверку входных данных, services — за бизнес-логику, а views — за HTTP-взаимодействие.

В качестве базы данных выбрана PostgreSQL. Она хорошо интегрируется с Django, поддерживает транзакции, индексы, связи между таблицами и JSON-поля. JSONField используется для хранения metadata, model versions, reasons и summary признаков. Это удобно для ML-прототипа, где часть служебных данных может изменяться по мере развития модели. Хранение сериализованных моделей в `BinaryField` PostgreSQL упрощает развёртывание: не требуется отдельная файловая система или объектное хранилище.

Для ML-части используются scikit-learn и XGBoost. Scikit-learn предоставляет реализацию Isolation Forest, используемую для персональных моделей поведенческих аномалий. XGBoost применяется для классификации phishing URL на основе набора признаков. Библиотека joblib обеспечивает сериализацию и десериализацию sklearn-моделей в байтовый буфер для хранения в базе данных.

Frontend реализован с использованием React и TypeScript. React позволяет быстро создавать интерактивный пользовательский интерфейс, а TypeScript повышает надёжность кода за счёт статической типизации. Frontend отвечает за страницы входа, enrollment, dashboard и форму транзакции с challenge-typing wizard-ом. При этом финальные решения безопасности остаются на backend-стороне.

Django Admin используется как инструмент демонстрации и аудита. Через административную панель можно просматривать пользователей, поведенческие сессии, события клавиатуры и мыши, phishing events, transaction attempts, risk assessments и BehaviorProfile. Это особенно полезно при подготовке дипломной демонстрации, поскольку позволяет показать внутренние данные системы без разработки отдельного сложного интерфейса администратора.

Для тестирования применяется pytest и pytest-django. Автоматические тесты покрывают extractor-ы, detector-ы, training pipeline, cache, API, behavior collection, dashboard privacy, transaction flow и decision matrix. Наличие полного набора тестов важно, поскольку система состоит из нескольких связанных подсистем, и изменение одной части не должно ломать остальные. По состоянию на текущую реализацию тестовый набор насчитывает 277 тестов.

## 2.9. Применение принципов SOLID

При проектировании системы особое внимание уделялось разделению ответственности между компонентами. Это важно, поскольку приложение объединяет web API, хранение данных, ML-инференс, feature extraction, кэширование и frontend-взаимодействие. Если смешать эти обязанности в одних и тех же классах, система быстро станет трудно сопровождаемой и плохо тестируемой.

Принцип единственной ответственности проявляется в разделении модулей по задачам. Например, phishing extractor-ы отвечают только за вычисление признаков URL. `FeatureCache` отвечает только за кэширование `URLFeatures`. `XGBoostPhishingDetector` отвечает за применение ML-модели. Аналогично в behavior-модуле: `BehaviorFeatureExtractor` отвечает за преобразование событий в признаки; `BehaviorProfileTrainer` отвечает за обучение и сохранение модели; `BehaviorAnomalyDetector` отвечает только за инференс. Transaction service использует результат анализа, но не занимается низкоуровневым подсчётом признаков.

Принцип открытости/закрытости проявляется в возможности добавлять новые extractor-ы без переписывания всей phishing-подсистемы. В behavior-подсистеме добавление нового поведенческого сигнала (например, scroll dynamics) требует только расширения `BehaviorFeatureExtractor` и добавления поля в `BehaviorFeatures` — decision logic остаётся неизменной.

Принцип инверсии зависимостей реализуется через service layer и detector abstractions. Высокоуровневая логика транзакций не зависит от конкретного способа извлечения признаков или конкретной ML-модели. Она работает с нормализованными результатами: phishing decision, phishing score, behavior decision и anomaly score. Это позволяет в будущем заменить Isolation Forest на другую модель без изменения transaction API.

Принцип подстановки Лисков проявляется в том, что `BehaviorAnomalyDetector` ведёт себя корректно как в обученном состоянии (возвращает `legitimate` или `anomalous`), так и в необученном (`suspicious`). Внешний transaction service получает совместимый `BehaviorAnomalyResult` в обоих случаях, что позволяет использовать mock-объекты в тестах и упрощает проверку decision logic.

С точки зрения тестирования SOLID-подход оказался особенно важным. Так как feature extraction, training, detector-ы, services и views разделены, каждый компонент можно тестировать отдельно. Phishing extractor-ы тестируются без API. Detector тестируется с mock-моделью. API-тесты мокают detector. Transaction tests мокают phishing и behavior results, чтобы проверить decision matrix.

## 2.10. Практическое применение системы и сценарии внедрения

Разрабатываемая система рассматривается не как изолированное демонстрационное web-приложение, а как прототип дополнительного слоя безопасности для критических пользовательских операций. Её практическое назначение состоит в том, чтобы дополнять традиционные механизмы аутентификации анализом поведения пользователя и контекста транзакции. Такой подход особенно актуален в ситуациях, когда пароль или одноразовый код были скомпрометированы, но злоумышленник не способен воспроизвести привычное поведение владельца аккаунта.

В реальной информационной системе предложенный механизм может выполнять роль risk engine. Он получает данные о текущей операции, анализирует поведенческую сессию пользователя с помощью персонализированной модели, проверяет связанный URL или источник операции на признаки phishing и формирует итоговое решение: разрешить операцию, потребовать дополнительную проверку или заблокировать действие.

Первым сценарием практического применения является цифровой банкинг. В банковских системах критическими действиями являются денежные переводы, добавление нового получателя, изменение лимитов, смена контактных данных и подтверждение платежей. Если сумма перевода велика, получатель новый, поведение пользователя аномально, а URL или контекст операции выглядит подозрительно, система может запросить дополнительное подтверждение или заблокировать операцию.

Вторым сценарием является электронная коммерция. В e-commerce системах аналогичный подход может применяться при оплате заказа, изменении адреса доставки, добавлении новой банковской карты или изменении данных аккаунта. Третьим сценарием являются корпоративные системы, где критическими операциями могут быть изменение прав доступа, работа с персональными данными или подтверждение финансовых заявок.

Практическая ценность предложенной системы заключается в том, что она не заменяет существующие средства защиты, а дополняет их. Пароль, MFA, session management и серверная авторизация остаются обязательными элементами безопасности. Поведенческий анализ и phishing detection выступают как дополнительный адаптивный слой.

Отдельным преимуществом является объяснимость решения. В отличие от полностью непрозрачной модели, текущая реализация сохраняет причины принятого решения: phishing decision, behavior decision, anomaly score, phishing probability, сумму транзакции и список reasons. Это важно для аудита, расследования инцидентов и демонстрации работы системы.

При этом следует учитывать ограничения прототипа. Для промышленного использования необходимо накопление достаточного количества поведенческих данных, настройка порогов, защита от обхода collector-а, интеграция с MFA и юридическая оценка обработки поведенческих данных. Тем не менее реализованный прототип демонстрирует ключевой принцип: транзакция должна оцениваться не только по факту успешного входа, но и по поведению пользователя и безопасности контекста операции.

## 2.11. Выводы по главе

Во второй главе была рассмотрена архитектура разрабатываемой системы аутентификации транзакций на основе AI. Была сформулирована постановка задачи, определены функциональные и нефункциональные требования, описаны основные пользовательские сценарии и выделены ключевые подсистемы приложения.

Было показано, что система строится вокруг гибридной оценки риска. В отличие от классического подхода, при котором транзакция разрешается после успешного входа пользователя, предложенная архитектура учитывает дополнительные сигналы: phishing-риск целевого URL и аномальность поведения пользователя относительно его персональной модели. Это позволяет реализовать более гибкий risk-based подход к аутентификации транзакций.

Модель данных включает сущности для хранения пользователей, поведенческих сессий, событий клавиатуры, событий мыши, персональных поведенческих профилей (`BehaviorProfile`), phishing-проверок, попыток транзакций и оценок риска. Особое внимание уделено приватности: система не хранит исходные введённые символы, а использует временные характеристики, хеши и агрегированные признаки.

Подсистема phishing-детекции реализует pipeline извлечения признаков URL, кэширование дорогостоящих проверок, применение XGBoost-модели и аудит результата. Подсистема поведенческого анализа преобразует события пользователя в числовой feature vector, обучает персональную Isolation Forest модель через `BehaviorProfileTrainer` и сохраняет её в `BehaviorProfile`. При инференсе модель загружается через `BehaviorAnomalyDetector.from_user_profile()` с автоматической проверкой версий и cold start fallback.

Механизм оценки риска транзакции объединяет phishing decision, behavior decision и параметры операции. Проблема несоответствия доменов обучения и инференса решена через challenge-typing: пользователь вводит контрольную фразу `.tie5Roanl` перед отправкой транзакции, что обеспечивает поведенческие данные в том же домене, что и enrollment. Итоговая decision matrix формирует одно из трёх решений: `ALLOW`, `CHALLENGE` или `DENY`.

Также была обоснована технологическая база проекта: Django, Django REST Framework, PostgreSQL, scikit-learn (Isolation Forest), joblib, XGBoost, React, TypeScript и pytest. Выбранный стек позволяет реализовать полноценный end-to-end прототип, объединяющий backend, frontend, ML-инференс, аудит и автоматическое тестирование.

Важным результатом проектирования стало разделение ответственности между компонентами. Feature extraction (`BehaviorFeatureExtractor`), training (`BehaviorProfileTrainer`), inference (`BehaviorAnomalyDetector`), persistence (`BehaviorProfile`), services, API и frontend collector реализованы как отдельные части системы. Это соответствует принципам SOLID, повышает тестируемость и создаёт основу для дальнейшего развития приложения.

Таким образом, во второй главе была сформирована архитектурная база для практической реализации системы. Следующая глава посвящена описанию программной реализации отдельных модулей, включая backend-приложение, phishing detection, сбор поведенческих событий, behavioral AI, transaction flow и frontend-интерфейс.
